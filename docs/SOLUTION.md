# Datathon 26 · ForteBank — решение команды

AI-сервис для выявления признаков нарушений кассовой дисциплины по видео. Всё работает **локально**: никаких облачных LLM/API, веса моделей скачиваются один раз, после этого сервис работает без интернета.

## 1. Как пользоваться

- **Веб-интерфейс:** открыть публичный адрес сервиса, загрузить `.mov`, дождаться статуса «Готово». Для каждого нарушения показываются тип, таймкод, 1–3 кадра-доказательства, описание и ссылка на правило.
- **API для жюри** (ключ передаётся в заголовке `X-API-Key`):

```bash
curl -X POST https://<адрес>/api/v1/analyze -H "X-API-Key: <ключ>" -F "file=@video.mov"
# -> {"job_id": "..."}
curl https://<адрес>/api/v1/jobs/<job_id> -H "X-API-Key: <ключ>"
# -> {"status": "done", "verdict": "violation" | "no_violation", "violations": [...]}
```

Формат ответа строго соответствует разделу 10 ТЗ (`type`, `timecode_sec`, `description`, `evidence_frames[{timestamp_sec, image_base64}]`). Подробнее — [API.md](API.md).

## 2. Запуск (macOS, Apple Silicon)

```bash
bash scripts/mac_setup.sh   # один раз: Python, FFmpeg, Node, cloudflared, сборка UI, .env, веса моделей
bash scripts/run_mac.sh     # API + воркер + публичный туннель; Mac не уходит в сон
```

`run_mac.sh` печатает публичный адрес `https://….trycloudflare.com` и сохраняет его в `logs/public_url.txt`. API-ключ лежит в `.env` (`JURY_API_KEY`). Скрипт можно запускать повторно: старые процессы останавливаются сами. Если туннель оборвётся, он перезапустится, но **адрес сменится** — актуальный всегда в `logs/public_url.txt`. Mac должен оставаться включённым, в сети и с открытой крышкой.

Обучение на датасете (видео и `open_labels.xlsx` лежат в `../data`):

```bash
.venv/bin/python scripts/extract_features.py ../data        # кадры 2 к/с + признаки, кэш в cache/
.venv/bin/python scripts/train.py ../data/open_labels.xlsx  # кросс-валидация, порог, модель -> models/scorer.joblib
# параметры по умолчанию (LR C=1.0, PCA 16, pos-tol 4 c) воспроизводят выложенную модель
```

## 3. Архитектура

```
Браузер / жюри ──► FastAPI (API + UI) ──► очередь SQLite ──► воркер (отдельный процесс, дедлайн 285 с)
                                                              │
     FFprobe/FFmpeg: проверка видео, 2 кадра/с по реальным PTS ◄┘
                                                              │
     CV-детектор (backend/app/detectors/cv.py):
       1. RT-DETR r18 (COCO): люди, телефоны, сумки            — Apache-2.0
       2. DINOv2-small: эмбеддинг сцены по каждому кадру       — Apache-2.0
       3. Временной классификатор (scikit-learn): вероятность нарушения по кадру,
          сглаживание, пики выше порога -> события; голова типа -> тип нарушения
       4. Эвристики: телефон в зоне кассира ≥ 2 кадров подряд
                                                              │
     Сопоставление тип -> правило (config/violation_types.json -> config/rules.json)
     Кадры-доказательства (JPEG), описание, правило, ограничения -> вердикт
```

**Почему так.** У M1 с 8 ГБ нет мощного GPU, а мультимодальные LLM на нём обрабатывают видео дольше 5 минут. Поэтому мы используем две лёгкие модели (~1 ГБ RAM, CPU/MPS) и обученный на разметке классификатор. Ролик длиной 145 с при 2 к/с даёт ~290 кадров.

**Порог** подбирается кросс-валидацией с исключением целых видео: сначала **ноль пропущенных роликов с нарушением** (по FAQ пропуск недопустим), затем минимум ложных срабатываний. После этого порог дополнительно сдвигается на 0.05 в сторону полноты: финальное видео снято под другим углом.

**Возможности развития:** дообучение на новых ракурсах, замена эмбеддера на видео-модель (VideoMAE), трекинг рук и денег, добавление зон «касса / сейф» под конкретное помещение.

## 4. Нормативная база

Основной источник — **Правила осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей в БВУ…**, утв. постановлением Правления НБРК от 29.11.2019 № 231 (рег. МЮ РК № 19680), https://adilet.zan.kz/rus/docs/V1900019680. Текст сверен по редакции на zakon.uchet.kz (обновлено 12.07.2026).

| Правило (id) | Пункт | Суть требования |
|---|---|---|
| NBRK231-P20-COUNT | п. 20 | Наличные принимаются и пересчитываются **в присутствии клиента** |
| NBRK231-P20-STORAGE | п. 20 | Принятые наличные хранятся в **запираемых устройствах** (шкаф, сейф, ящики) |
| NBRK231-P22-LEAVE | п. 22 | Нельзя **покидать рабочее место** до окончания обслуживания клиента |
| NBRK231-P12-PERSONAL | п. 12 | Личные вещи и деньги работников — **вне кассового узла**; связь только без фото/видео |
| NBRK231-P24-25-COLLECTOR | пп. 24–25 | Проверка **целостности сумки и пломбы** инкассации; вскрытие — при инкассаторе |
| NBRK231-P5-ACCESS | п. 5 | Кассовые операции — в **специально оборудованных помещениях** кассового узла |

Где цитата неполная, в карточке правила это помечено как «Изложение». Ссылок без источника нет. Каждый вывод сформулирован как **признак возможного нарушения** для проверки человеком.

## 5. Типы нарушений

| Тип | Что видно на видео | Правило |
|---|---|---|
| `count_without_client` | Кассир пересчитывает или держит деньги вне поля зрения клиента (на коленях, у лица) | п. 20 |
| `cash_unattended` | Деньги или инкассаторская сумка лежат открыто на столе без присмотра или при следующем посетителе | п. 20 |
| `leave_cash_room` | Кассир уходит из кассового помещения, оставив рабочее место или ценности | п. 20 |
| `cash_to_pocket` | Кассир перемещает купюры в карман или к личным вещам | п. 12 |
| `personal_items` | Кассир вносит или кладёт на рабочее место личные вещи (сумку, верхнюю одежду) | п. 12 |
| `food_at_workplace` | Кассир ест или пьёт на рабочем месте рядом с наличными | п. 12 |
| `safe_left_open` | Дверца сейфа или шкафа для наличных остаётся открытой | п. 20 |
| `phone_in_cash_zone` | В руках или на рабочем месте кассира телефон | п. 12 |
| `collector_bag` | Сумка инкассации принята без видимой проверки пломбы при инкассаторе | пп. 24–25 |
| `outsider_in_cash_room` | Во время обслуживания входит посторонний и взаимодействует с кассиром | п. 5 |
| `leave_workplace` | Кассир отходит от рабочего места, пока клиент не обслужен | п. 22 |

Типы определены вручную по обучающим роликам (`config/event_types.json`), потому что в разметке организаторов есть только флаг нарушения и секунда.

## 6. Ограничения и известные ошибки

- **Качество по leave-videos-out CV (5 фолдов, 42 ролика, 22 с нарушением):** `LR C=1.0, PCA 16, pos-tol 4 c`, порог 0.55 → TP 22, **FN 0**, FP 17, TN 3 (accuracy 0.60), медианная ошибка таймкода 3.7 c; в сервисе порог 0.5. Порог выбран под требование «пропуск хуже ложного срабатывания», поэтому большинство чистых роликов тоже помечаются. AUC «ролик с нарушением / без» по максимуму вероятности около 0.45–0.56 во всех испробованных конфигурациях: на таком объёме данных модель отличает ролики почти на уровне случайного угадывания, а ценность её в основном в подсказке таймкода внутри ролика.
- **Время:** ролик 142 c на Mac M1 8 ГБ обрабатывается примерно за 50 c (с холодной загрузкой моделей), ролики 15–20 c — за 12–16 c.

- **Мало данных:** 42 ролика, по одному нарушению в каждом. Редкие типы (1–2 примера) классифицируются ненадёжно; при неуверенности тип выбирается по самому частому классу.
- **Другой ракурс:** эмбеддинг сцены чувствителен к смене камеры. Частично это компенсируют ролики с двух ракурсов в обучении и сдвиг порога, но ложных срабатываний может стать больше.
- **Мелкие объекты:** пломба, номинал купюр и содержимое экрана сверху почти не видны. Такие проверки (сверка документов, суммы, проводки) сервис **не делает и не утверждает**.
- **Нарушения бездействием** (не проверил пломбу, не запер ящик) отмечаются по моменту, когда видно последствие (инкассатор ушёл, кассир отошёл).
- **Частота кадров 2 к/с:** очень короткие действия (< 0.5 с) могут быть пропущены.
- **Распознавания лиц нет** (запрещено ТЗ), люди различаются только по положению в кадре.
- Результат — **подсказка для проверяющего**, не юридическое заключение.
